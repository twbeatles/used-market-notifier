## User Scenarios & Testing *(mandatory)*

### User Story 1 - 백업 복원이 데이터를 망가뜨리지 않는다 (Priority: P1)

사용자가 설정 > 유지보수에서 백업을 선택해 복원하면, 모니터링이 먼저 안전하게 멈추고, 복원된 데이터베이스가 정확히 백업 시점 내용으로 바뀌며, 앱을 다시 켰을 때 정상적으로 열린다.

**Why this priority**: 현재 복원은 데이터베이스를 손상시키거나 조용히 무효화한다. 데이터 보호 기능이 데이터를 파괴하는 것은 가장 심각한 결함이다.

**Independent Test**: 앱이 데이터베이스를 연 상태에서 추가 기록을 남긴 뒤 이전 백업을 복원하고, 재시작 후 무결성과 행 수를 확인한다.

**Acceptance Scenarios**:

1. **Given** 앱이 실행 중이고 백업 이후 매물 300건이 더 기록된 상태, **When** 그 백업을 복원하고 앱을 다시 열면, **Then** 데이터베이스 무결성 검사가 통과하고 매물 수는 백업 시점과 같다.
2. **Given** 모니터링이 실행 중, **When** 복원을 요청하면, **Then** 복원 전에 모니터링이 완전히 멈추며, 멈추지 못하면 복원이 거부되고 사용자에게 이유가 표시된다.
3. **Given** 복원 직전 상태, **When** 복원이 끝나면, **Then** 복원 직전 데이터 전체(최근 변경 포함)를 담은 되돌리기용 사본이 남는다.

### User Story 2 - 알림은 실제로 새로 올라온 매물에만 온다 (Priority: P1)

사용자가 모니터링 중에 키워드를 추가·수정·재활성화해도 이미 올라와 있던 매물이 한꺼번에 알림으로 쏟아지지 않는다. 설정을 저장해 모니터링이 재시작되어도 그 사이 올라온 새 매물 알림이 누락되지 않는다. 예외적으로 많은 새 매물이 한 번에 나오면 개별 알림 대신 요약 알림이 온다.

**Why this priority**: 가장 흔한 사용 흐름에서 스팸 또는 누락이 발생하며, 외부 메신저의 발송 제한까지 유발한다.

**Independent Test**: 모니터링 사이클을 두 번 돈 뒤 키워드를 추가하고 다음 사이클의 알림 수를 센다. 모니터링 재시작 직후 새로 등장한 매물 1건의 알림 여부를 확인한다.

**Acceptance Scenarios**:

1. **Given** 모니터링이 여러 사이클 진행된 상태, **When** 새 키워드를 추가하면, **Then** 그 키워드의 첫 검색 결과는 알림 없이 저장되고, 이후 새로 등장한 매물만 알림이 간다.
2. **Given** 어떤 플랫폼의 첫 검색이 실패한 상태, **When** 이후 처음 성공하면, **Then** 그 결과는 알림 없이 기준선으로 저장된다.
3. **Given** 모니터링 중, **When** 설정을 저장해 모니터링이 재시작되면, **Then** 재시작 후 첫 사이클에서 새로 등장한 매물도 알림이 간다.
4. **Given** 한 키워드·플랫폼에서 한 사이클에 알림 상한을 넘는 새 매물이 나오면, **When** 알림을 보내면, **Then** 상한까지만 개별 알림을 보내고 나머지는 건수를 담은 요약 알림 1건으로 보낸다.
5. **Given** 앱을 새로 켠 첫 사이클, **When** 검색이 끝나면, **Then** 기존 정책대로 알림 없이 저장된다.

### User Story 3 - 설정 화면의 유지보수·차단 관리가 실제로 동작한다 (Priority: P1)

사용자가 설정 > 차단 관리에서 차단한 판매자 목록을 보고 해제할 수 있고, "지금 정리 실행" 전에 모니터링 중지 확인을 받는다. 정리 후 목록·통계가 새로고침된다.

**Why this priority**: 현재 차단 해제가 불가능하고, 정리·복원이 모니터링과 동시에 실행된다.

**Independent Test**: 판매자를 차단한 뒤 설정 > 차단 관리에서 목록 1건 확인 → 해제 → 0건.

**Acceptance Scenarios**:

1. **Given** 판매자 1명이 차단된 상태, **When** 차단 관리 탭을 열면, **Then** 1건이 표시되고 해제하면 목록에서 사라지며 다음 사이클부터 해당 판매자 매물이 수집된다.
2. **Given** 모니터링 실행 중, **When** "지금 정리 실행"을 누르면, **Then** 모니터링 중지 확인을 받고 중지 후에만 정리가 진행된다.

### User Story 4 - 가격·판매 상태 기록이 정확하다 (Priority: P2)

"가격문의"처럼 가격을 알 수 없는 값이 들어와도 이미 알고 있는 실제 가격을 덮어쓰거나 가짜 가격 변동 알림을 만들지 않는다. 확인된 판매완료/예약중 상태는 상태 단서가 없는 검색 결과 한 번에 되돌아가지 않는다. 오래된 데이터베이스의 가격 숫자값은 전부 올바르게 재계산된다.

**Why this priority**: 가격 변동 알림과 통계의 신뢰도를 직접 좌우한다.

**Independent Test**: 같은 매물을 "35만원 → 가격문의 → 35만원" 순서로 저장하고 가격 변동 기록 수를 센다.

**Acceptance Scenarios**:

1. **Given** 실제 가격이 저장된 매물, **When** 가격을 알 수 없는 값으로 다시 수집되면, **Then** 가격은 유지되고 가격 변동으로 기록되지 않는다.
2. **Given** 가격 미상으로 저장된 매물, **When** 실제 가격이 처음 확인되면, **Then** 가격은 채워지지만 가격 변동 알림은 가지 않는다.
3. **Given** "1만원"인 매물, **When** "무료나눔"으로 바뀌면, **Then** 실제 가격 변동으로 기록된다.
4. **Given** 판매완료로 확인된 매물, **When** 상태 단서가 없는 결과로 다시 수집되면, **Then** 판매완료 상태가 유지된다.
5. **Given** 가격 숫자값이 오래된 규칙으로 계산된 1,200건의 매물, **When** 앱을 시작하면, **Then** 1,200건 모두 재계산된다.
6. **Given** 상세 보강으로 가격 텍스트가 바뀐 매물, **When** 저장되면, **Then** 가격 숫자값도 새 텍스트 기준으로 저장된다.

### User Story 5 - 모니터링 중지·재시작이 빠르고 안전하다 (Priority: P2)

중지 버튼을 누르면 화면이 멈추지 않고 즉시 "중지 중" 상태로 바뀌며, 진행 중이던 사이클은 남은 키워드를 더 검색하지 않고 끝난다. 재시작은 이전 모니터링이 완전히 끝난 뒤에만 시작된다. 앱 종료 시 백그라운드 작업이 끝난 뒤 데이터베이스가 닫힌다.

**Why this priority**: 현재 최대 10초 화면 멈춤과 중복 엔진 실행 위험이 있다.

**Independent Test**: 키워드 3개로 검색 중 중지 요청 → 추가 검색 횟수와 중지 소요 시간을 측정한다.

**Acceptance Scenarios**:

1. **Given** 첫 키워드 검색 중, **When** 중지하면, **Then** 이후 키워드 검색은 시작되지 않고 화면은 0.2초 이상 멈추지 않는다.
2. **Given** 이전 모니터링이 정리 중, **When** 사용자가 다시 시작하면, **Then** 정리가 끝난 뒤 자동으로 시작되며 동시에 실행되는 모니터링은 항상 1개 이하다.

---

### User Story 6 - 브라우저 자원을 낭비하지 않는다 (Priority: P2)

대체(폴백) 엔진이 없거나 필요하지 않을 때 브라우저를 반복해서 끄고 켜지 않으며, 대체 엔진 브라우저는 실제로 필요해질 때 처음 띄운다.

**Why this priority**: 사이클 시간 급증, 메모리 낭비, 봇 탐지 노출을 줄인다.

**Independent Test**: 대체 엔진이 없는 설정에서 상세 보강 10건 수행 시 브라우저 생성 횟수를 센다.

**Acceptance Scenarios**:

1. **Given** 대체 엔진이 없는 플랫폼, **When** 상세 보강 10건을 수행하면, **Then** 주 엔진 브라우저는 새로 만들어지지 않는다.
2. **Given** 모니터링 시작 직후, **When** 아직 대체 엔진이 필요하지 않으면, **Then** 대체 엔진 브라우저는 실행되지 않는다.
3. **Given** 대체 엔진 생성이 실패한 플랫폼, **When** 같은 사이클에서 다시 필요해지면, **Then** 일정 시간 동안 재시도하지 않는다.

---

### User Story 7 - 어디서 실행해도 같은 데이터를 쓰고, 한 번만 실행된다 (Priority: P2)

작업 스케줄러·다른 폴더의 터미널·시작 위치가 다른 바로가기로 실행해도 프로그램 폴더의 설정과 데이터베이스를 사용한다. 로그 파일을 쓸 수 없어도 앱은 시작된다. 이미 실행 중일 때 다시 실행하면 안내 후 종료된다. Windows 명령줄 모드에서도 기본 브라우저 엔진을 사용할 수 있다.

**Why this priority**: "데이터가 사라졌다"는 오인과 자동 실행 조용한 실패, 중복 실행으로 인한 알림 중복을 막는다.

**Independent Test**: 다른 작업 폴더에서 실행해 사용 중인 설정 파일 경로를 확인한다. 두 번째 실행 시 종료되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 쓰기 권한이 없는 작업 폴더, **When** 앱을 실행하면, **Then** 앱이 정상 시작되고 프로그램 폴더의 데이터를 쓴다.
2. **Given** 앱이 실행 중, **When** 다시 실행하면, **Then** "이미 실행 중" 안내 후 두 번째 실행이 종료된다.
3. **Given** Windows 명령줄 모드, **When** 모니터링을 시작하면, **Then** 기본 브라우저 엔진 사용이 가능하다.

---

### User Story 8 - 저장된 비밀값과 내보낸 파일이 안전하다 (Priority: P3)

알림용 봇 토큰과 웹훅 주소는 Windows에서 사용자 계정에 묶인 방식으로 암호화되어 저장되고 백업에도 암호화된 상태로 들어간다. 설정 저장 도중 앱이 강제 종료되어도 설정 파일이 잘리지 않는다. 엑셀/CSV로 내보낸 매물 제목은 수식으로 실행되지 않는다.

**Why this priority**: 보안·데이터 보호 보강이며, 즉각적 기능 실패보다는 위험 감소 성격이다.

**Independent Test**: 설정 저장 후 파일에 토큰 원문이 없는지 확인하고, 재로드 시 원래 값이 복원되는지 확인한다. "=1+1" 제목을 내보내 셀이 문자열인지 확인한다.

**Acceptance Scenarios**:

1. **Given** Windows에서 토큰을 입력해 저장, **When** 설정 파일을 열어 보면, **Then** 토큰 원문이 보이지 않고 앱 재시작 후 알림은 정상 동작한다.
2. **Given** 기존 평문 토큰이 있는 설정 파일, **When** 앱을 시작하면, **Then** 그대로 읽히고 다음 저장 시 암호화된다.
3. **Given** 다른 컴퓨터에서 가져온 암호화 토큰, **When** 복호화에 실패하면, **Then** 해당 값은 비워지고 사용자에게 재입력 안내가 표시되며 앱은 정상 시작된다.
4. **Given** "=HYPERLINK(...)" 제목의 매물, **When** 엑셀/CSV로 내보내면, **Then** 수식이 아닌 문자열로 저장된다.

### User Story 9 - 오래된 매물 정리가 여전히 보이는 매물을 지우지 않는다 (Priority: P3)

정리 기준은 "마지막으로 검색 결과에서 본 시각"이다. 오래전에 처음 발견됐지만 여전히 검색 결과에 나오는 매물은 삭제되지 않아 재알림되지 않는다. 같은 검색어라도 설정(플랫폼·지역)이 다른 키워드는 검색 간격을 따로 계산한다.

**Why this priority**: 정리 후 재등록·재알림과 간격 판정 혼선을 없애는 보강이다.

**Independent Test**: 40일 전에 처음 발견됐지만 오늘도 검색된 매물이 30일 정리에서 남는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 40일 전 최초 발견, 오늘 다시 검색된 매물, **When** 30일 기준 정리를 실행하면, **Then** 삭제되지 않는다.
2. **Given** 40일 전 최초 발견 후 한 번도 다시 보이지 않은 매물, **When** 정리하면, **Then** 삭제된다.

### Edge Cases

- 복원할 백업의 데이터베이스가 손상되었거나 형식이 다르면 복원은 실패하고 현재 데이터는 그대로 유지된다.
- 복원 중 오류가 나면 되돌리기용 사본이 남고 현재 데이터베이스는 변경 전 상태로 남는다.
- 키워드 필터(지역·가격 범위·제외어)를 바꾸면 새 조건의 첫 검색은 기준선으로 저장된다.
- 모니터링 중지가 제한 시간 안에 끝나지 않으면 강제 취소하되 앱 종료 시에는 끝날 때까지 기다린다.
- 이전 실행이 비정상 종료되어 남은 실행 잠금은 자동으로 무시된다.
- Windows가 아닌 환경에서는 비밀값 암호화를 적용하지 않는다(기존 동작 유지).
- "0원"·"무료나눔"은 알 수 없는 가격이 아니라 실제 가격으로 취급한다.

## Requirements *(mandatory)*

### Functional Requirements

**데이터 보호 (ISSUE-001, ISSUE-003, ISSUE-007)**

- **FR-001**: 복원은 열려 있는 데이터베이스 연결과 쓰기 로그를 고려한 일관된 방식으로 수행되어야 하며, 복원 후 재시작 시 무결성 검사가 통과해야 한다.
- **FR-002**: 복원 직전 데이터 전체(쓰기 로그에만 있던 최근 변경 포함)의 되돌리기용 사본을 만들어야 한다.
- **FR-003**: 복원과 수동 정리는 실행 중인 모니터링을 먼저 완전히 중지해야 하며, 중지를 확인할 수 없으면 거부해야 한다.
- **FR-004**: 설정 화면은 호스트 창을 올바르게 찾아 차단 판매자 목록 조회·해제, 정리 후 새로고침을 수행해야 한다.
- **FR-005**: 가격 숫자값 재계산 마이그레이션은 행 수와 무관하게 모든 행을 처리해야 하며, 이전 버그로 부분 처리된 데이터베이스도 한 번 더 재계산되어야 한다.

**알림 정확성 (ISSUE-002, ISSUE-004, ISSUE-011)**

- **FR-006**: 시스템은 (키워드, 검색 조건, 플랫폼) 단위로 첫 성공 검색을 기준선으로 영구 기록하고, 기준선이 없는 검색 결과는 알림 없이 저장해야 한다.
- **FR-007**: 앱 최초 시작의 첫 사이클은 기존처럼 알림을 보내지 않고, 앱 실행 중의 모니터링 재시작 후에는 첫 사이클부터 알림을 보내야 한다.
- **FR-008**: 한 키워드·플랫폼당 한 사이클의 개별 알림은 상한(15건)을 넘지 않아야 하며, 초과분은 요약 알림 1건으로 전달해야 한다.
- **FR-009**: 알림이 억제된 새 매물은 트레이 알림도 표시하지 않아야 한다.
- **FR-010**: 알 수 없는 가격 값은 알려진 가격을 덮어쓰거나 가격 변동으로 기록되지 않아야 하며, 미상 → 실제 가격은 알림 없이 채워져야 한다.
- **FR-011**: 상세 보강으로 가격 텍스트가 바뀌면 가격 숫자값도 새 텍스트 기준이어야 한다.
- **FR-012**: 명시적 판매 상태가 없고 제목에 상태 단서가 없으면 기존 판매 상태를 유지해야 한다.

**런타임 안정성 (ISSUE-005, ISSUE-006, ISSUE-009, 갭)**

- **FR-013**: 모니터링 중지 요청은 UI를 블로킹하지 않아야 하며, 진행 중 사이클은 다음 키워드·플랫폼 처리 전에 중단되어야 한다.
- **FR-014**: 백그라운드 모니터링 스레드는 종료가 확인될 때까지 참조가 유지되어야 하고, 재시작은 이전 스레드 종료 후에만 시작되어야 한다.
- **FR-015**: 앱 종료·복원·정리·업데이트 적용은 모니터링 종료를 기다린 뒤 진행해야 한다.
- **FR-016**: 대체 엔진이 없는 플랫폼의 보강은 주 엔진을 재생성하지 않아야 한다.
- **FR-017**: 대체 엔진은 처음 필요할 때 생성되어야 하고, 생성 실패 시 일정 시간(10분) 재시도를 멈춰야 한다. 대체 엔진 이상 시 주 엔진은 유지한 채 대체 엔진만 재생성해야 한다.
- **FR-018**: Windows 명령줄 모드는 브라우저 엔진이 요구하는 하위 프로세스 지원 이벤트 루프를 사용해야 하며, 폐기 예정 이벤트 루프 정책 API를 사용하지 않아야 한다.
- **FR-019**: 키워드별 사용자 지정 검색 간격은 검색어·플랫폼·지역 조합 단위로 판정해야 한다.

**환경·보안 (ISSUE-008, ISSUE-010, 갭)**

- **FR-020**: 설정·데이터베이스·로그·백업·디버그 출력의 기준 폴더는 실행 작업 폴더와 무관하게 프로그램 폴더여야 한다.
- **FR-021**: 로그 파일을 열 수 없어도 앱은 시작되어야 한다.
- **FR-022**: GUI는 사용자 세션당 하나만 실행되어야 하며, 두 번째 실행은 안내 후 종료되어야 한다(스모크 검사 모드 제외).
- **FR-023**: 설정 저장은 원자적으로 수행되어 중단 시에도 이전 또는 새 설정 중 하나가 온전히 남아야 한다.
- **FR-024**: Windows에서 알림 비밀값(봇 토큰, 웹훅 주소)은 사용자 계정 기반 암호화로 저장되어야 하며, 기존 평문 설정은 그대로 읽혀야 한다. 복호화 실패 시 값을 비우고 사용자에게 알려야 한다.
- **FR-025**: 내보낸 엑셀/CSV의 모든 텍스트 셀은 수식으로 해석되지 않아야 한다.
- **FR-026**: 정리 기준은 매물을 마지막으로 검색 결과에서 본 시각(없으면 최초 발견 시각)이어야 한다.

**문서**

- **FR-027**: README·CLAUDE.md의 테스트 수, 복원·알림 정책 설명, 비동기 패턴, 퍼지 중복 설명, GUI 바인딩 예제가 실제 구현과 일치해야 하며, 에이전트 지침 파일은 대소문자 구분 파일시스템에서도 찾을 수 있어야 한다.

### Key Entities

- **검색 기준선 (Search Baseline)**: 검색어, 검색 조건 서명(지역·가격 범위·제외어), 플랫폼, 기준선 확정 시각. 이 조합의 결과를 알림 대상으로 볼지 결정한다.
- **매물 마지막 확인 (Listing Last Seen)**: 매물 식별자와 마지막으로 검색 결과에서 본 시각. 정리 기준으로 쓴다.
- **복원 사본 (Pre-restore Snapshot)**: 복원 직전 데이터베이스의 일관된 전체 사본.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 앱이 데이터를 기록 중인 상태에서 복원해도 재시작 후 무결성 검사 통과율 100%, 매물 수가 백업 시점과 100% 일치한다.
- **SC-002**: 모니터링 중 키워드를 추가한 다음 사이클에서 기존 매물 알림 0건.
- **SC-003**: 모니터링 재시작 직후 사이클에서 새로 등장한 매물 알림 누락 0건.
- **SC-004**: 한 키워드·플랫폼당 사이클 개별 알림 최대 15건 + 요약 1건.
- **SC-005**: "35만원 ↔ 가격문의" 반복 수집 시 가짜 가격 변동 기록 0건.
- **SC-006**: 중지 요청 시 화면 멈춤 0.2초 미만, 중지 후 추가 키워드 검색 0회.
- **SC-007**: 대체 엔진이 없는 플랫폼에서 보강 10건 수행 시 주 엔진 재생성 0회.
- **SC-008**: 차단 판매자 해제 성공률 100%.
- **SC-009**: 쓰기 불가 작업 폴더에서의 앱 시작 성공률 100%.
- **SC-010**: 전체 자동화 테스트 통과 및 이번 결함 재현 시나리오가 모두 회귀 테스트로 포함된다.

## Assumptions

- 앱 최초 시작 시 첫 사이클 알림 억제는 README에 명시된 의도된 정책이므로 유지한다. 억제 대상은 앱 실행 중 재시작이 아닌 "프로세스 시작 후 첫 모니터링"으로 한정한다.
- 알림 상한은 키워드·플랫폼·사이클당 15건으로 고정하며 설정 항목으로 노출하지 않는다.
- 필터 조건을 바꾸면 새 기준선이 필요하다고 본다. 조건 변경 직후 첫 검색의 진짜 신규 매물 1사이클분 알림 누락은 폭주보다 나은 절충으로 받아들인다.
- 기존 테이블 구조 변경 금지 규칙에 따라 기준선·마지막 확인 시각은 새 테이블로만 추가한다.
- 스크래퍼 파싱 로직과 봇 탐지 우회 모듈은 수정하지 않는다. 가격·상태 교정은 엔진·저장 계층에서 처리한다.
- 비밀값 암호화는 Windows 사용자 계정 보호 기능을 사용하며, 다른 컴퓨터로 옮긴 백업의 비밀값은 재입력이 필요하다.
- 프로그램 폴더는 패키징 실행 파일이면 실행 파일 폴더, 소스 실행이면 저장소 루트다(업데이터와 동일 기준).
- 실제 사이트 스모크, 메신저 실제 발송은 이 작업의 자동 검증 범위에서 제외한다.
